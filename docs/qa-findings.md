## F-03 · S3 性能 · 大库上保留期清扫 57 秒（2026-10-23，probe-bigdata 首跑）

- **复现**：probe-bigdata（20000 条、时间散布 0-45 天）→ 设 HistoryRetentionDays=7
  触发清扫 → **57381ms** 才完成（约 17k 条删除，均摊 3.4ms/条）。预算 10s，超 5.7 倍。
- **影响**：清扫在后台跑不冻 UI，但 57 秒的写事务与用户的新增写入竞争——大库用户
  第一次触发保留期会有一分钟的写入卡顿窗口。
- **根因（代码走读）**：RetentionService.SweepHistory 逐条删（每条一个事务）+ 每条
  联动删原图文件（逐文件 IO）。批次之间没有合并事务。
- **建议（修复期）**：整批一个事务 + 原图文件删除移出事务；或分批（每批 500 条）
  之间让出。预期 57s → 亚秒级（批量事务）。
- **探针状态**：perf:bigdata-retention 保持 FAIL（预算 10s 编码需求，不放宽）。
- **已修（2026-10-23）**：上面的根因走读不成立——SweepHistory 本来就是一条 `DELETE … WHERE created_at
  BETWEEN`，一个事务。真正的根因是 `entries.translated_from`（指向原条目，`ON DELETE SET NULL`）没有
  索引：每删一行，SQLite 都要扫一遍全表找指向它的行，删一万七千行就是一万七千次全表扫描。补上
  `idx_entries_translated_from`（不看版本号，`IF NOT EXISTS`）后，同样 2 万条、清掉 16872 条：
  **68233ms → 583–625ms**（本机 Core 基准，三次）。回归测试：StorageScaleTests 钉住这条索引在
  「已标为当前版本的库」上也会建出来，且外键查找走它。管理窗按时间段删除、清空历史、大库删单条同样受益。

## F-07 · 发现 · 设置翻转受 store 字段依赖约束（2026-10-23，settings-cycle 首跑）

- **现象**：一次 TryUpdateSettings 里同时翻转四个开关——BarEdgeDock 与
  AutoBackupEnabled 的翻转未生效（保持默认），RecordImages/TranslateBadge 成功。
- **根因（推断）**：store 层的字段依赖校验——edge-dock 需要父开关（钉住）先行；
  AutoBackupEnabled 的开启需要备份文件夹配置。悬空的翻转被回退。
- **修正**：探针改为分步翻转（先父开关、再子开关、备份补文件夹路径）。
- **测试价值**：这条依赖链本身就是给用户的文档素材（设置页的父子关系说明）。

## F-08 续 · 邮箱行芯片为空的机理（2026-10-23 深挖）

- **行间的钉住态级联**：每行的收尾 TakeDown 对**钉住的预览无效**（Pinned 拒收），
  预览带着钉住态与上一行的卡片进入下一行；下一行的 ShowFor 命中
  「钉住的预览不换卡」提前返回——预览一直显示上一行的卡片与芯片。
- **表现**：行 J（邮箱）读到的芯片是行 I（图片）的 copy-image——除非行间的
  拔钉把状态带回来。行 J 的 chips= 空：行 I 的拔钉把工作台拆到只剩
  空列表的中间态。
- **修复方向（产品侧，本轮不动）**：ShowFor 对钉住的预览收到新卡时，
  先拆工作台再重灌（或钉住态下直接换卡重灌芯片）。探针侧行间已显式拔钉
  （ForceFreshPreviewAsync 模式）的行不再互相污染。
- **状态**：F-08 待查收窄到「钉住态跨行级联 + 芯片重灌时序」。
