# ADR-0003：划词取词的路线与触发

- 状态：已接受
- 日期：2026-09-21

## 背景

划词翻译需要拿到用户在**任意应用**中选中的文本。只有两条路：UI Automation
（`IUIAutomation` + `TextPattern`）或模拟 `Ctrl+C` 后读剪贴板。

本应用同时在监听剪贴板（ADR-0001 的功能 #2），因此模拟 `Ctrl+C` 与自身职责直接冲突。

**注意**：本决策在未完成技术调研的情况下作出。UIA 在 Chromium 系、Electron、
Java/Qt、PDF 阅读器中的实际覆盖率**未经一手来源核实**，仅凭先验判断。

## 决策

1. **只用模拟 `Ctrl+C`**，不实现 UIA 路径。取舍：牺牲干净性，换取近乎 100%
   的应用覆盖率与单一代码路径。
2. **划词由显式热键触发**，不做"选中即取词"。

第 2 条是第 1 条推导出的必然结果：纯 `Ctrl+C` 路线下，判断"用户是否选中了文本"
的唯一手段就是真的复制一次。因此"选中就冒徽标"等价于"每次鼠标抬起都偷偷动剪贴板"，
不可接受。UIA 路线没有这个鸡生蛋问题（可只查询不取），但已被第 1 条排除。

## 后果

以下四项由本决策强制要求，均非可选：

1. **剪贴板保存/还原** — 取词前保存、取完还原。多格式（图片/文件列表/RTF）
   完美还原极难，现实做法是保文本格式，异类格式接受有损。
2. **自我抑制标志** — 剪贴板监听器必须忽略自己造成的变化。
   `WM_CLIPBOARDUPDATE` 异步到达，该标志的生命周期需谨慎设计。
3. **轮询等待** — `SendInput(Ctrl+C)` 之后**没有事件**告知目标应用已写入剪贴板，
   只能轮询加超时。等太短取不到、等太长发木。**这是全应用最脆的一点**，
   也是"偶尔吃掉用户真实剪贴板内容"这类难复现 bug 的来源。
4. **提权应用无法取词** — 前台窗口若为管理员权限进程而本应用不是，`SendInput`
   被 UIPI 阻挡。任务管理器、管理员终端中划词无反应。这是硬边界，不是缺陷。

选择热键触发，把第 3 条的时序风险从"每次拖选"降到"每次真实意图"，
暴露面小一个量级。

## 被推翻的备选

- **UIA 优先 + `Ctrl+C` 兜底** — 常见情况走干净路径，覆盖率最高。因需实现
  两条路径而被放弃。
- **只用 UIA** — 与功能 #2 零冲突、代码最干净，但部分应用中直接无反应。
- **先写探针实测 UIA 覆盖率再定** — 该问题讨论不出答案、只能实测；用户选择
  跳过，直接采用覆盖率确定的方案。
- **鼠标抬起即取词** — 体验最自动，但每次拖选都动剪贴板。

## 附记：UIA 取词 spike（2026-10-17，评审 F-11 · D4）

用 `spikes/UiaSpike` 量了 `TextPattern.GetSelection` 在四个应用的测试文档上读选区的准确度
（各 20 次，不碰剪贴板、不发键盘，选区用 UIA 自己的 FindText + Select 做再读回）：

| 应用 | 读对 / 20 | 备注 |
|---|---|---|
| 记事本 | 20 | Single；Document 控件 |
| Word | 20 | Multiple；Document 控件 |
| Edge | 4 | 选区整体偏 1–2 字符，Chromium 端点毛病是系统性的 |
| VS Code | 未测成 | 一次性用户目录的启动被并进已开着的实例，无法隔离 |

**结论：维持本 ADR 的取向不变**——Ctrl+C 路线仍是唯一对所有应用一视同仁的路。UIA 只在原生文本
控件里靠得住；若将来做 UIA 加速，另开实现票：维护白名单（记事本、Word 一类），白名单命中先试
UIA、失败即回落 Ctrl+C；其余应用一律照旧。
