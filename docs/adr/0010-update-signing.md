# ADR-0010：更新包签名（ECDSA P-256，零新依赖）

- 状态：已接受
- 日期：2026-10-01
- 补充：票 28（GitHub Releases 更新通道）

## 背景

票 28 的更新通道会下载 GitHub Releases 上的安装包，校验大小、可选的 SHA-256 和压缩包结构，
然后交给第二个进程替换安装目录。2026-10-01 的评审发现两个问题：

1. 默认通道指向的 GitHub 账号无人注册，任何人都能抢注后发布"新版本"（已在 81064a0 修正为
   本仓库 `youguoda/shiyu`）。
2. 信任根本身是空的：校验和文件来自同一个发布，能篡改安装包的人也能篡改校验和；
   取不到校验和时还会直接放行（fail-open）。应用随开机自启，被替换的程序就是常驻进程。

## 决策

1. **发布时对安装包签名**：用 ECDSA P-256 对 `shiyu-win-x64.zip` 的完整字节签名，签名以
   `shiyu-win-x64.zip.sig` 随发布上传。使用 .NET 内置的 `System.Security.Cryptography.ECDsa`，
   不引入任何新依赖。
2. **客户端内置公钥**，先验签、后解压。没有签名、签名不符、取不到签名，一律拒绝安装，
   并清空暂存区。**没有任何 fail-open 路径。**
3. **私钥只存在于 GitHub Actions 的加密 secret 中**（以及作者离线保存的一份备份），
   不进仓库、不进任何日志。
4. 发布构建不读取 `SHIYU_UPDATE_API` 一类的环境变量覆盖；它们只在调试构建中生效。
5. Authenticode 代码签名证书暂不购买。等到有外部用户、需要消除 SmartScreen 警告时再评估。

## 后果

- 私钥一旦丢失，就无法再发布能被自动更新接受的版本，用户只能手动下载新版本。
  缓解：离线备份私钥。
- 换钥：新版本内置新公钥，并且这个版本本身用旧私钥签名。旧客户端用旧公钥验过它，
  装上之后就认新公钥。
- SHA-256 校验和保留，用于下载完整性检查和人工核对，但它不再承担信任。
- 2026-10-22 补充：每个正式版另附 `latest.json`（与 API `releases/latest` 同形），匿名 API
  被限流（按出口 IP 每小时 60 次）时客户端改取它，可经镜像。它不签名：清单只决定"去哪下、
  下多大"，被篡改的结果顶多是装不上，信任仍只在安装包字节的验签上。
