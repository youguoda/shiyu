# ADR-0011：API 密钥用 DPAPI 保护，备份默认不含密钥

- 状态：已接受
- 日期：2026-10-01
- 补充：ADR-0007（历史的两个入口，与不加密的取舍）

## 背景

ADR-0007 决定历史库**不加密**，依赖 Windows 账户隔离，并把"SQLCipher 整库加密 + DPAPI 管密钥"
列为第一顺位的回头选项。那次权衡的对象是**剪贴板历史**。

翻译服务的 API 密钥是另一类数据：它代表用户的付费账户，泄露的后果是被盗刷，而不只是
被看到。2026-10-01 的评审发现：

1. 密钥以明文存在 `settings.json` 里；
2. "不加密导出"的备份会带上整份设置，密钥也就跟着出去了。备份文件是最容易离开这台电脑的东西。

## 决策

1. **只对密钥本身使用 DPAPI**（`ProtectedData`，`DataProtectionScope.CurrentUser`）。
   设置文件里存保护后的 Base64，不再存明文。首次加载时自动把旧的明文迁移过去。
2. **备份默认不含密钥。** 只有"加密导出"时，才提供"同时导出 API 密钥"的选项。
   因为 DPAPI 的密文换了机器或换了用户就解不开，所以导出时写入的是加密备份内部的明文，
   导入时再用本机 DPAPI 重新保护。
3. 历史库仍按 ADR-0007 **不加密**；本 ADR 不推翻它。

## 后果

- 把设置文件复制到另一台电脑或另一个 Windows 用户下，密钥会失效，需要重新填写。
  这是期望的行为：密钥不应该随一个文件漫游。
- 改动很小（约 20 行），不引入新依赖，对用户透明。

## 补充（2026-10-04，v3 票 29）：密钥只发给它所属的服务商

DPAPI 保护的是密钥在磁盘上的样子，管不到它被发往哪里。自备密钥只有一个格子，不记它是为哪家
服务商填的：在设置里切换预设（`applyPreset` 只改预设、地址、模型）、在"测试连接"里把凭据框
留空（回落到已存的密钥）、或手动把服务地址改成另一家，都会把 A 家的密钥作为
`Authorization: Bearer` 发给 B 家的服务器。对方回 401，但密钥已经交到了第三方手里。Xtranslate
用"按服务商分格存密钥"防的正是这件事（`docs/research/2026-09-27-xtranslate-analysis.md` §7）。

决策：

1. 设置里多一个明文字段 `BackendApiKeyOrigin`：保存密钥时服务地址的 scheme + host + port。
   来源不是秘密。**只比来源、不比路径**——同一家服务商常有多个路径前缀（`/v1`、
   `/compatible-mode/v1`），改个路径不该让密钥失效；不同的服务商从不共用主机。
2. 请求前一律经 `AppSettings.KeyFor(baseUrl)` 取密钥：来源一致才返回，否则空串。
   `AppSettings.Backend` 据此取密钥，来源不一致时 `Backend.IsConfigured` 为 false，请求不发，
   面板走"还没有配置"的引导卡。写密钥只经 `AppSettings.WithApiKey`，密钥与来源成对写下
   （设置窗「保存凭据」、引导里填的密钥）。没有记下来源的密钥同样不被带上：失败即关闭。
3. 旧设置文件里有密钥、没有来源：加载时以当时的服务地址补上（维持现有的配对），下次保存时落盘。
4. 备份：来源随设置一起走。备份不带密钥时（默认），恢复保留**本机**的密钥与来源（决策 2 的
   语义不变，加上来源）；备份自己带了密钥，就照单全收，来源随它来。

后果：

- 切到别家后，原密钥仍留在设置里但不会被发出；切回原来那家，来源又一致，自动恢复可用。
- 凭据框下方提示"已保存的密钥属于 {旧主机}，请填写 {当前服务商} 的密钥"；「测试连接」在
  凭据框留空且已存的密钥属于别家时不发请求，给出第四种人话结果（不算失败）。
- 单格仍是单格：在 B 家填了新密钥，A 家的就被覆盖，切回 A 家要重填。按来源分格存多把密钥
  （即 Xtranslate 的按服务商密钥库）是日后的选项，要连带改 DPAPI 落盘与备份剥密，等有真实
  需求再做。

## 补充（2026-10-10）：每家服务商各存一份凭据，可以显示

上一节留的"日后的选项"有了真实需求：用户要记得保存凭据、能看到凭据、知道配过哪些服务商、方便切换。

决策：

1. 单格换成按来源分格：`AppSettings.SavedProviders`，每家一份（来源、地址、上次用的模型、
   预设 Id、凭据），按来源至多一份。`KeyFor` 按来源在里面找，"只发给它所属的那一家"不变；
   写入口仍只有 `WithApiKey`——记在此刻服务地址的来源名下，别家的一份不碰，空密钥是删掉这一家。
2. 落盘：每份凭据各自经 DPAPI 保护，打不开的那份整份丢弃（同决策 1 的"当作没有"）。旧版的
   `BackendApiKey` / `BackendApiKeyOrigin` 只为读旧文件而留，加载时并入 `SavedProviders`
   （来源与当时的地址一致就连地址、模型一起记下），之后不再写回。
3. 备份：不带密钥时（默认）整张表都不带——没有凭据的"一家"什么也恢复不了；恢复时保留本机的
   整张表。带密钥时（只在加密包里）照单全收，替换本机的表。
4. 切换：服务商下拉里存过的标「✓ 已保存」，选中回到上次的地址与模型；"已保存的服务商"列表
   里点「切换」同样。当前这家的地址、模型改了，跟着记下。
5. 显示与复制：界面打码显示（开头 6 位与末尾 4 位，短的只给圆点），点「显示」才看全、换一家
   就收起；完整的密钥不可选中，复制只走「复制」——拾语自己的写入口，带
   `ExcludeClipboardContentFromMonitorProcessing`、`CanIncludeInClipboardHistory=0`、
   `CanUploadToCloudClipboard=0`，不进拾语的历史、Windows 剪贴板历史与别的剪贴板工具。

后果：

- 存 B 家的密钥不再顶掉 A 家的；切回 A 家不用重填。
- "已保存的凭据不回显"这条老规矩换成"打码显示、点开才看全"：看得到是用户要的，代价是肩窥与
  截屏的风险，由默认打码与"换一家就收起"压住。
- 凭据框下方的提示改说"还没有保存 {这家} 的凭据"——别家的都还在，不再是"属于别家"。
