# 07 — 常驻内存上涨与呼出延迟超预算

**来源：** 接手时读数 + 测试矩阵 §4 性能预算
**Status:** ready-for-agent

**现象（都是实测，命令见发布清单「内存读数」与票 22）：**
- 0.17.5 同一进程：17:43 工作集 107 MB（运行约 6.7 h）→ 18:42 工作集 168 MB、私有 294 MB（约 7.7 h）。0.16.1 跑 12 h
  是 106 / 184 MB。私有高约六成，过了发布清单「高出两成先查原因」的线。0.17.0–0.17.4 发布时都没记读数，涨在哪一版不知道。
- 热呼出 P95 215–248 ms（预算 150），冷呼出 P95 748 ms（预算 600），均为 Debug 构建、2026-10-16。
- 两个门槛别混：评审 F-21 的 300 ms 是「改不改轻量模式」的触发线；150 ms 是测试计划的预算。

**What to build:**
1. 查因：0.17.0 以来新常驻的东西——离线词典（3.7 MB 的 SQLite）、OCR 后台、自然音色、预览工作台、定期备份。
   用同一套合成数据跑 0.16.1 与 0.17.5 各 1 小时比对私有内存（探针数据目录隔离，不碰用户数据）；必要时抓一次
   托管堆快照看谁在长。
2. 让 Release 也能量热呼出：现有 `summon-timing` 是 DEBUG 命令。注意 O-41：Release 程序集不许出现 `SHIYU_` 字面量，
   开关不能走环境变量，得另想（例如只读日志事件的时间差）。
3. 预算要不要改（150 / 600 ms）由用户定；在那之前矩阵如实标「超预算」。

**验收：** 查因结论写进本票；若找到可修的涨点，修后同条件复测，私有内存回到 0.16.1 的两成以内；Release 热呼出有一组数。

## Comments

- 2026-10-21 查因（全部实测；测量工具是 `%TEMP%` 下的一次性小程序，不进仓库）：
  - **托管堆只有 12.5 MB**（对正式实例 dotnet-gcdump 一次，13 万个对象）。291 MB 私有几乎全是原生内存，不是 C# 对象泄漏。
  - **句柄按类型清点**（只读系统句柄表）：5019 个里 **Event 4314**、EtwRegistration 263、File 128、Key 59、Thread 40。
    托管的等待句柄只有 7 个——事件对象是原生代码建的。观察到一次 GC 后句柄 6336 → 5019、私有 294 → 267 MB 同时掉。
  - **OCR 与语音不是元凶**：独立程序里 OCR 首次识别 +10 MB / +60 句柄、连认 20 次不再涨；OneCore 朗读首次 +9 MB /
    +400 句柄、连读 10 次不涨。
  - **窄条重建不漏**：探针实例 `summon-timing` 连呼 42 次（轻量开关各 21 次），Event 一直约 1720，一个没涨。
    顺带的热呼出（Debug）：轻量 P50 82 / P95 212 ms，稳态 P95 131 ms。
  - **启动路径很克制**：临时插桩逐步记句柄（测完撤掉），空闲探针启动完只有 392 个；跳变发生在**第一扇窗显示**时。
  - **根因：WPF 硬件渲染在这台机器上的固定开销**。一扇空白 WPF 窗口：硬件渲染私有 +78 MB、句柄 +1138、线程 +11；
    第二扇只再 +15 MB / +3 句柄；软件渲染只 +6 MB / +97 句柄。这台机器有 AMD 核显 + 向日葵的虚拟显卡（OrayIddDriver），
    D3D 初始化由驱动的用户态组件拉起大批线程与事件。正式实例比探针多出的两千多个事件，最可能来自 D3D 设备丢失后的
    重建（锁屏、睡眠、远程桌面切换），且 GC 后能部分回收——**这一条未直接证实**。
- **结论**：没有找到拾语自己的泄漏。可以在拾语侧动手的只有一条——改用 WPF 软件渲染（`RenderOptions.ProcessRenderMode`
  或逐窗 `HwndTarget.RenderMode`），在这台机器上约省 70 MB 私有与一千多个句柄；代价是动画与长译文流式重排改由 CPU 画。
  要不要做是产品取舍：先用 `probe-stream-jank`（流式卡顿预算）与 `measure-hot-summon` 在软件渲染下各量一遍，用户看数再定。
- 预算一栏（工作集 ≤ 120 MB）在硬件渲染下、这台机器上很难达标：一扇空白窗口就占去约 80 MB 私有。
